## 老项目里的「改一处崩一片」

在 Flask/Django 单体里改认证库，常见翻车链：只改 `auth.py` 却忘了测试里的 mock、文档里的示例、CI 镜像里的依赖 pin。人脑容易漏，Agent 若 **没有计划阶段** 也会漏，只是漏得更快。Plan Mode 强制先输出 **文件级清单与验证命令**，你再点头，才把风险从「未知」变成「可见」。

## Plan Mode 在做什么

交互上，你用 `/plan` 或自然语言要求「先计划再执行」。Agent 应返回：

- 拟修改路径列表
- 依赖与测试影响
- 建议执行的命令
- 明确不碰的目录

你确认后，它再进入编辑与 shell。社区反馈（如多文件 JWT 迁移案例）显示，有计划时返工次数明显下降，尤其当仓库有基本测试时。

## 简化案例：库替换的检查表

任务：把 `PyJWT` 换成 `python-jose`，保持对外 API。

**计划阶段你必须看到**：

- `requirements.txt` 或 `pyproject.toml`
- 所有 `import jwt` / `PyJWT` 文件
- `tests/` 下认证相关用例
- README 或 API 文档片段

**执行阶段你应盯着**：

- diff 是否出现无关格式化
- 测试是否真跑过（看终端输出，不信口头「已通过」）

更完整的分阶段表见本站《Plan Mode：跨文件重构从计划到验收》。

## 三条直接改 vs 三条先 plan

**可直接改**（仍建议小步提交）：

- 单文件 typo、注释、日志文案
- 已有测试覆盖的纯函数内部实现
- 代码生成后你立刻肉眼 diff 的 20 行内改动

**必须先 plan**：

- 认证、支付、权限模型
- 跨 3+ 目录或涉及数据库迁移
- 删文件、改公共 API、升 major 依赖

## 计划文本里应出现的五类信息

审计划时除了文件列表，还应看到：**依赖版本策略**（pin 还是 range）、**测试范围**（全量还是受影响包）、**回滚触发条件**（哪类测试红就停）、**数据迁移**（有无不可逆 SQL）、**文档与 changelog** 是否更新。缺一类就要求 Agent 补 plan，不要带着空洞计划开干。

## 与 Code Review 文化的配合

Plan Mode 不是替代 CR，而是让 CR 聚焦在业务判断。推荐在 PR 描述里贴 Plan 摘要链接或折叠块，审查人先扫计划再扫 diff，能显著减少「改了一堆看不懂」的合并。

## 何时 /plan、何时直接改

| 信号 | 建议 |
|------|------|
| 触及 3+ 文件 | 先 Plan |
| 改生产配置 | 先 Plan + 人审 |
| 单行 typo | 直接改 |
| 不熟悉目录 | 先 Plan 列清单 |

Plan 输出要含 **不改动列表**，防止 Agent 顺手重构无关模块。

## Plan 会话验收

- 是否列出依赖文件与测试命令  
- 是否标风险（迁移、破坏性 API）  
- 人是否逐条勾选后再执行  

缺一项就继续问，不要「看起来很长」就批准。

## 与 Code Review 衔接

把 Plan 摘要贴进 PR 描述，Reviewer 对照实际 diff。若 diff 超出 Plan 范围，要求 Agent 解释或回滚。

## Plan 失败后的降级

若 Plan 两轮仍含糊，缩小范围到单目录或单模块，不要硬扩到全仓。若测试命令本身不存在，先让人补测试脚手架，再让 Agent 改业务代码。否则 Plan 再漂亮也是空中楼阁。

## 与结对编程配合

一人持键盘批准工具调用，一人看 Plan 勾选。Agent 适合「驾驶员-导航员」模式，不适合无人看守的长时间循环。

## Plan 模板片段

```text
目标：
不动：
必跑测试：
风险：
回滚：
```

每次 Plan 必填五项，Agent 输出缺项则要求补全后再执行。

## 实操附录：Plan 评审会

选一张中等复杂度 ticket，只允许 `/plan` 输出，禁止写代码。评审会 20 分钟勾选：文件列表完整、测试命令存在、风险有回滚。通过后才开执行会话。连续两次 Plan 漏测的开发者，先补测试再允许 Agent 改码。

## 读者可执行检查

对下一张中等 ticket 强制先 `/plan`，评审通过后再执行。连续跳过 Plan 两次则暂停 Agent 写库一周。

## 发布前核对

下一张 ≥3 文件 ticket 必须附 Plan 勾选截图。无 Plan 的 PR 模板应勾选拒绝。

## 会后跟进

Plan 模板合并进 issue 模板，新建 ticket 自动带五项清单占位。

## 版本记录

Plan 五项模板若缺「回滚」，评审直接退回。回滚可以是 git revert 命令一行，但不能空白。

## 局限与不适合谁

Plan 质量依赖模型对仓库的理解；无测试、无 README 的仓库，计划也会瞎。若团队文化是一路「确认全部」，Plan 退化为仪式。极短脚本仓库用 Plan 反而慢。最新子命令以 [官方 Hooks/Plan 文档](https://code.claude.com/docs) 为准。
