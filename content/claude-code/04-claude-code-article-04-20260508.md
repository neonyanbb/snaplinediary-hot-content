## 先核对：你的版本到底有没有这些项

Anthropic 的迭代节奏快，Focus Mode、Live Preview、Slack 集成等功能的可用性因账号类型、平台、CLI 版本而异。Pro 账号与免费账号、桌面端与终端 CLI、v0.x 与 v1.x 之间的功能差异可能很大。开通前务必在应用内设置或 code.claude.com/docs/en/features-overview 核对，避免文章写了你却找不到按钮。

终端 CLI 用户可以用 `claude --version` 确认版本，桌面端用户在菜单栏看 About。功能缺失时不要反复重试，先升级或确认订阅档位。

## Focus Mode：减少上下文切换

Focus Mode 目前主要在桌面端提供，开启后会收缩侧边栏与通知区域，把界面焦点集中在对话流与代码 diff 上。适合需要连续 45 分钟以上深度工作的场景，比如跨模块重构、批量补测试、或读 legacy 代码做逆向工程。

实测感受：对「维持心流」有帮助，但不替代 Plan Mode。Focus Mode 解决的是界面干扰问题，Agent 该漏的文件仍然会漏。建议开启前先写清「本会话只完成 X」，结束条件设为测试全绿或 PR 开完。防止「开 Focus 一整天却无合并」的虚假忙碌。

如果你主要用终端 CLI，Focus Mode 并不适用。终端用户可以用 tmux 的 `tmux new -s deepwork` 或终端全屏达到类似效果。

## Live Code Preview：前端反馈环

Live Preview 让 Agent 在修改前端代码后，自动打开本地 dev server 的页面截图或浏览器预览。适合组件库、静态页、Vite / Next.js 等能本地 `npm run dev` 的项目。你可以在会话里直接说「改完这个组件后截图预览」，Agent 会尝试启动 dev server 并抓取页面状态。

局限也很明显：后端 API 路由、批处理脚本、CLI 工具的收益几乎为零，因为这些没有可视界面。预览依赖本地环境能跑起来，如果 `node_modules` 缺失或端口被占，预览会失败。SSR、WebSocket、需要鉴权 cookie 的页面也常出问题，遇到「预览正常、生产异常」时，必须回到真实环境测，不要迷信预览截图。

建议在前端项目的 `CLAUDE.md` 里写明固定端口，比如：

```
本地 dev server 端口固定为 3000
预览 URL 模板: http://localhost:3000/components/button
```

这样 Agent 不需要猜测端口，减少随机端口导致的 E2E 失效。

## Model Picker：成本与质量平衡

Model Picker 允许在同一会话里切换不同档位的模型。策略上可以参考以下分层：

读全库、写 Plan 阶段用强模型。Plan 需要理解跨目录依赖，漏一个文件后续成本极高，这里不能省。

改样板测试、格式化、注释等机械任务用较弱模型。这些任务的上下文需求低，小模型通常足够。

同一任务失败两次后，升级模型而非无限重试。小模型反复失败消耗的 token 累加起来，可能比直接上大模型更贵。

建议记录一周账单。Claude Code 的用量在 Anthropic 控制台可见，按会话统计。对比「全用强模型」和「Plan 用大、执行用小」两种策略的总成本，用数据验证是否真省。不要凭感觉切换。

## Slack / Discord 集成：异步把关

Slack 集成让团队能在频道里收到 Agent 的计划摘要，成员可以回复「批准」或「拒绝」后再继续执行。适合分布式团队或技术负责人无法实时盯终端的场景。

配置时需要创建一个 Slack Bot，权限给最小集：读指定频道、发 thread 回复、可选 react。不要给 Admin 或全workspace 读取。仓库访问用 GitHub App 的细粒度权限，而不是个人 PAT，防止离职员工 token 泄露导致仓库暴露。

风险在于频道权限与信息泄露。敏感仓库的计划摘要可能包含文件路径、接口名称，甚至间接暴露架构信息。建议敏感项目用私有频道，且 Plan 摘要做脱敏处理，把具体业务名词换成泛化描述。

## 模型切换策略的实操

在会话开头声明模型档位，避免中途切换导致上下文风格断裂。比如：

```
/plan 用强模型
执行阶段用标准模型
如果测试失败两次，切回强模型 debug
```

这不是官方语法，而是给 Agent 的指令文本。实际切换方式以当期文档为准，可能是 `/model` 子命令或界面下拉菜单。声明的好处是：即使你自己忘了切，回头翻会话记录时也知道当时为什么选这个档位。

## 协作会话的权限边界

谁创建会话谁拥有终止权，访客只读。避免两人同时批准冲突的工具调用，尤其是 `write` 和 `bash` 类操作。如果公司要求安全审计，可以导出会话日志或开启录屏。

多人协作时，规则要明确：谁启动会话谁负责 merge。两人同时在一个分支上让 Agent 改代码，冲突概率接近百分之百。推荐做法是：一人持终端执行，另一人在 Slack 里审 Plan，形成「驾驶员-导航员」模式，而不是双人驾驶。

## 局限与不适合谁

Focus Mode 和 Live Preview 不提升模型本身的推理上限。一份烂计划加上专注模式，仍然是烂计划。协作集成引入新的攻击面，安全团队可能禁止 Slack Bot 访问代码仓库。如果你只用终端 CLI，桌面特性基本可以忽略，不需要为了 Focus Mode 去装桌面端。
